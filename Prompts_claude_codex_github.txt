You are acting as a Senior Principal Performance Test Architect with 15+ years of experience

1. Home page load (city autosuggest / source-destination selection)

3. Search results rendering (bus list with operator, seat availability, fare, boarding points)

7. Boarding/dropping point fetch

   - Define a realistic transaction mix based on production analytics assumptions, e.g.:

   - Model route popularity as a Pareto/long-tail distribution across the top ~20 city pairs 
     (e.g., Bangalore–Chennai, Hyderabad–Vijayawada, Mumbai–Pune, Delhi–Jaipur) rather than 
     uniform random source-destination selection — reflecting real demand concentration
   - Model peak vs off-peak traffic (festival season, weekend spikes, weekday troughs, 
     time-of-day booking curves e.g. 9-11 AM and 6-9 PM surges)
   - Include a configurable ramp-up/steady-state/ramp-down load profile

   - Provide a test architecture diagram description (load generator -> API gateway -> 
     search service -> cache -> DB/inventory service)
   - JUSTIFY your choice of load-generation engine — pure Python asyncio+httpx vs Locust

     "<1000 VUs: asyncio sufficient; >5000 VUs: distributed Locust/k6 workers required")
   - Identify critical business transactions (CBTs) for Redbus search flow
   - Define workload model: concurrent users, think-time, pacing, session correlation 
     (route search -> select bus -> seat -> boarding point as one user journey, not isolated calls)

     - "Search API p95 < 800ms — derived from mobile 3G abandonment research showing 
       >1s response drives >20% bounce on low-bandwidth connections typical of Tier-2/3 
       India users"
     - "Seat layout fetch p95 < 500ms — must complete within perceived-instant UI threshold 
       (Nielsen's 1-second response guideline) since it's mid-funnel, high-intent"
   - Provide the full metric table: Throughput (RPS/TPS per transaction), Response Time 
     (p50/p90/p95/p99), Concurrency (target VUs), Error rate (<0.1%), Latency budget

     to be validated against actual Redbus SLA/NFR document" rather than presenting it as fact

   - Search timeout / upstream inventory service slow response
   - Cache-miss storm (cold cache after deployment, TTL expiry stampede)
   - Partial inventory response (some operators' data unavailable — graceful degradation)
   - Downstream seat-layout service failure during high concurrency
